# FactorDB：面向大规模 agent 因子研究的因子库

状态：设计 + 第一阶段（日频）实现。范围：基于 QFinVerse 日频面板的 Assay（美股），第二阶段扩展到分钟线。

## 1. 为什么要做

现在的 Assay 评估一个因子时，先按一个股票池和区间加载「日期 × 证券」面板，再遍历表达式、打分。结果按（表达式, 股票池, 区间, 复权）缓存。一个研究员用没问题，几百个 agent 提出几万个因子就不行了：

| 问题 | 后果 |
|---|---|
| 结果按股票池和区间缓存 | SP500 2016–2026 算过的 `ts_mean(volume, 20)`，换成 NASDAQ100、换成 2018–2026、换一个 agent，都要重算 |
| 一个请求一个进程一份面板 | 32 核用不上，TOP3000 的一批因子卡在单线程 |
| 全程 float64 | 内存是源数据（float32）的两倍 |
| 区间开头的预热 NaN | 60 日窗口的因子，每次请求开头都丢 60 天 |
| agent 工具照搬人用的接口 | 一个因子一次阻塞调用、返回体大、agent 之间不去重、没有配额 |

## 2. 核心思路：在全局网格上只算一次

每个因子表达式都可以拆成两类计算：

* **按列可分**的部分：时序和逐元素算子（`ts_*`、`+ - * /`、`log`、`where` …）。证券 *s* 在 *t* 日的值只取决于 *s* 自己截至 *t* 的历史，**和股票池无关**。
* **按行耦合**的部分：截面算子（`cs_rank`、`cs_zscore`、`cs_neutralize`、分组算子）。值取决于当天截面里有哪些证券。

FactorDB 把按列可分的部分在一张**全局网格**上只存一份：存储期内的每个交易日 × 曾经属于最大股票池（TOP3000 ∪ 指数成分）的每只证券。任何股票池、任何区间的请求，都从网格里切出对应的行和列，再按该股票池当天的成分即时计算截面部分。截面计算每天一遍，比滚动窗口便宜得多。

```
cs_rank( ts_corr(close, volume, 20) )
         └──── 存在网格上 ────┘   每次请求按股票池成分计算
```

如果时序算子套在截面算子**外面**（`ts_mean(cs_rank(x), 5)`），结果依赖股票池，这类节点按股票池分别存储，仍然在区间和 agent 之间共享。

### 2.1 规范形式与身份

计算之前先解析并规范化：可交换算子（`add`、`mul`、`elem_min`、`elem_max`、`eq`、`ne`、`and`、`or`）的参数排序，数字字面量统一，窗口取整与引擎一致。规范树的结构哈希就是**因子 id**。两个 agent 分别写 `close/open` 和 `div(close, open)`，得到同一个 id；提交已知 id 不花任何计算。

### 2.2 节点存储

每个存储节点是网格上的一个 float32 矩阵，按**年份分块**（`nodes/<hash>/<year>.npy`，内存映射读取）。按年分块让追加很便宜（只重写当年），读取也快（读 2016–2026 只映射 11 个文件）。年块按**证券优先**存放（`证券数 × 天数`）：工作进程按证券分片计算，写入的是连续区间；按股票池读取时每只证券读一段连续数据。（按日期优先存放时，每次写 25 列都会碰到文件的每一页，在 15 GB 内存的生产机上每个任务要读写几个 GB。）每个节点有一份 meta，记录规范表达式、所属网格、有效截至日、大小、计算耗时和命中次数（用于淘汰，也用于回答 agent 的「这个算过没有」）。

存哪些节点：

* 每个因子的**前沿**：最大的按列可分子树（第一个截面算子的输入；没有截面算子时就是整个因子）；
* 被两个及以上因子用到的按列可分子树（按节点统计热度）。

字段本身不复制，直接读 QFinVerse 面板的年块。

### 2.3 公司行动与时点正确性

QFinVerse 面板按成交原样存价，读取时复权到窗口最后一天的股本口径。FactorDB 在存储的最后一天 *E* 的口径上计算网格节点。结束日 *E′ < E* 的请求必须看到 *E′* 口径的值。对价格**齐次**的节点，两者只差一个按证券的常数：

* 面板对价格和成交量各有一个调整因子 `P`、`V`：`close/open/high/low` 的阶为 (1, 0)，`volume` 为 (0, 1)，`transactions`、`dvol`、`ret` 为 (0, 0)；
* 算子合成阶数：`mul` 相加，`div` 相减，`add/sub/min/max/where` 要求阶相同，`ts_mean/ts_sum/ts_std/ts_delay/ts_min/ts_max/abs/neg` 保持，`ts_corr/ts_rank/ts_returns/cs_*/sign/比较` 为 (0, 0)，非零阶的 `log/sqrt/pow` 没有阶；
* 阶为 (a, b) 的节点，按证券除以 `P^a · V^b` 即可，`P`、`V` 是 (*E′*, *E*] 之间公司行动的累积因子。

大多数 alpha 因子阶为 (0, 0)，不需要换算。没有阶的节点（如 `log(close)`）在结束日早于 *E* 的请求里不走网格，改用原引擎直接算。

面板发布新版本时 FactorDB **追加**：每个节点只算新增的日期，输入从新日期往前多取该节点的回看长度（各层窗口之和；`ts_ema` 这类递推没有上限，整列重算）。有新拆股或分红的证券整列重算，因为新事件改变了它复权后的全部历史。一般一天只有几十列，约 9,000 列里的零头。

## 3. 计算：按证券分片并行

一批表达式合成一张 DAG（共享子树只出现一次）。缺失的前沿节点由一组工作进程计算，每个进程负责一段证券：

1. 父进程把各节点的年块文件分配好（内存映射）；
2. 每个工作进程映射自己那几列的输入字段（QFinVerse 年块本来就是内存映射），用进程内的公共子表达式缓存算完这批所有缺失节点，直接写进输出文件的对应列；
3. 进程之间不传大数组，输入由操作系统页缓存共享。

时序算子各列互不依赖，所以可以随核数扩展，直到内存带宽成为瓶颈。截面层和打分（IC、RankIC、衰减、换手）在父进程按日向量化计算。

精度：输入为 float32，工作进程内用 float64 计算，存储为 float32。与原引擎的 IC 差异远小于 1e-4。

### 3.1 Spec pack（worker 的输入）

ADES worker 按 spec（股票池、区间）给因子打分。同一个 spec 的每个因子读的都是同一批输入：区间内当过成分股的全部证券的 OHLCV（按交易日对齐，复权到区间最后一天）、成分股掩码，以及各周期的前向收益。设置 `ASSAY_PACK_DIR` 后（worker 上是 `/var/cache/assay-worker/packs`），`assay.data.specpack` 按面板快照把它们存成 C 连续的 float64 `.npy`，只读映射打开：

| TOP1000 2016 年起（2723 × 2421） | 从面板读取 | spec pack |
|---|---|---|
| 加载 | 5.4 秒 | 约 0 秒（worker 上首次构建约 2 秒） |
| 55 个 Alpha101 因子打分的峰值内存 | 2.6 GB | 1.5 GB |
| 磁盘 | — | 460 MB |

打分结果逐位一致。pack 在第一次使用时构建（目录和每个前向收益文件都靠改名一次性出现），周期用到时再补；面板有新快照时生成新的 pack，并删掉旧快照的。同一台机器上的进程共享映射的页。

## 4. 面向 agent 的接口

为多个 agent 共享一台服务器而设计：

| 原则 | 做法 |
|---|---|
| 批量优先 | 一次提交几百个表达式，拿到 job id |
| 幂等 | 因子 id = 规范哈希；已知因子在已知规格上直接返回已有评分 |
| agent 之间共享 | 一个节点库、一个注册表；正在计算的重复请求合并到同一个任务 |
| 返回体小而稳定 | top-k 表格，字段固定；数值按需、抽样返回 |
| 错误可操作 | 每个拒绝都带错误码、表达式中的位置和修改建议 |
| 内置新颖度 | 用存储的值计算与因子库的相关性 |
| 公平使用 | 按用户排队、轮流调度，一个 agent 占不满全部算力；可选的每日计算上限（`ASSAY_FACTORDB_BUDGET_S`，默认不限） |
| 可追溯 | 每个因子记录提出者、时间、父因子和标签 |

### 4.1 MCP 工具（v2）

| 工具 | 用途 |
|---|---|
| `fdb_submit` | 在一个规格（股票池、区间、预测期）上评估大量表达式。立即返回 job id，以及重复、被拒（附建议）、已有评分的因子 |
| `fdb_job` | 进度、预计剩余时间、目前最好的因子、失败汇总 |
| `fdb_query` | 按指标、标签、提出者、新颖度筛选和排序已评分因子 |
| `fdb_factor` | 单个因子：规范形式、各规格评分、诊断、来源 |
| `fdb_novelty` | 一个表达式或 id 与因子库的最大相关性，以及最接近的几个因子 |
| `fdb_values` | 某日的截面快照（排名最高和最低的证券及数值），用于检查因子选出了什么 |
| `fdb_operators` | 算子目录：签名、类别、阶数规则 |
| `fdb_budget` | 调用者已用和剩余的计算量 |

MCP 服务也以 streamable HTTP 方式挂在 Assay 站点的 `/mcp/` 下，使用与 REST API 相同的账户和个人 API 密钥。远程 agent（Claude、Codex 等）都连到同一个 FactorDB。

### 4.2 REST

同样的操作在 `/v1/fdb/*` 下（`POST /submit`、`GET /jobs/{id}`、`GET /factors`、`GET /factors/{id}`、`POST /novelty`、`GET /values`、`GET /operators`、`GET /budget`）。

## 5. 分钟线（第二阶段）

分钟数据大两个数量级（MASSIVE 分钟聚合，2003–2026 年约 100 GB parquet）。设计沿用同样的组件，但并行单位从证券换成**交易日**：

* 分钟字段存储每天一块（常规交易时段 390 根 × 当天成分），float32，证券 id 与日频网格对齐；
* 日内表达式按天计算（时间轴是当天第几根 bar），各天之间没有依赖，可以并行；
* 主要用法是**把日内特征归约成日频值**，即 `day_agg(expr, "last" | "mean" | "sum" | "std" | …)`。结果进入日频节点库，可以和日频算子自由组合（`cs_rank(day_agg(ts_corr(close, volume, 30), "mean"))`）；
* 只有分钟级回测需要时，才按天存完整的分钟输出。

## 6. 阶段

1. **日频 FactorDB**：规范 id、全局网格、节点库、按证券分片并行计算、追加与公司行动重算、注册表与任务、REST 和 MCP v2、带账户鉴权的 HTTP MCP。与现有引擎做基准对比。
2. **分钟线**：分钟字段存储构建、按天的日内计算、`day_agg`、分钟回测。
3. **横向扩展**：按「代价 × 命中」淘汰；节点库放共享卷供多台计算机使用；面板每次更新后定时预算因子库的前沿节点。
